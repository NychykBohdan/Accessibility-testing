# A11Y-REPORT — звіт про проблеми доступності saucedemo.com

| | |
|---|---|
| **Об'єкт** | https://www.saucedemo.com (користувач `standard_user`) |
| **Стандарт** | WCAG 2.1, рівень AA (додатково зазначено рекомендації рівня AAA та best practice) |
| **Дата перевірки** | 2026-11-19 / 2026-11-20 |
| **Інструменти** | Playwright 1.65, axe-core 4.14 (`@axe-core/playwright`), Chromium / Firefox / WebKit, ручна перевірка DevTools |
| **Автотести** | Кожна проблема, підтверджена автотестом, має `test.fail()` з посиланням на свій ID |

## Підсумок

Автоматичне сканування axe (теги `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`) **не знайшло жодного порушення** на 7 сторінках і 7 станах UI. Проте клавіатурні тести та ручна перевірка виявили **11 проблем**. Одна з них **повністю блокує** покупку для користувачів, які працюють лише з клавіатурою. Це наочно показує межі автоматизації: axe перевіряє розмітку, а не взаємодію.

## A11Y-001

**Немає видимого індикатора фокуса на жодному елементі**

- **Сторінка/стан:** усі сторінки (login, inventory, item, cart, checkout, меню)
- **Опис:** глобальне правило `:focus { outline: none; }` (а також `.error-button:focus { outline: none; }`) прибирає стандартне кільце фокуса браузера. Альтернативного стилю (`:focus-visible`, `box-shadow`, зміна рамки чи фону) немає. На знімку екрана після Tab неможливо визначити, де саме фокус.
- **Критерій WCAG:** 2.4.7 Focus Visible (AA)
- **Кого зачіпає:** користувачів клавіатури, перемикачів (switch access), людей зі слабким зором і когнітивними порушеннями.
- **Кроки відтворення:**
  1. Відкрити https://www.saucedemo.com.
  2. Натиснути Tab кілька разів.
- **Очікувано:** сфокусований елемент має помітний індикатор (контраст ≥ 3:1 до сусідніх кольорів).
- **Фактично:** візуально нічого не змінюється; `getComputedStyle(el).outlineStyle === 'none'`, `boxShadow === 'none'`.
- **Рекомендація:** прибрати глобальне `:focus { outline: none }` або замінити його, наприклад: `:focus-visible { outline: 3px solid #132322; outline-offset: 2px; }`.
- **Severity:** High
- **Джерело:** клавіатура (`tests/keyboard/focus-visible.keyboard.spec.ts`) + ручна перевірка CSS

## A11Y-002

**Посилання на кошик недоступне з клавіатури**

- **Сторінка/стан:** шапка всіх авторизованих сторінок
- **Опис:** кошик реалізовано як `<a class="shopping_cart_link" role="button" aria-label="Cart, …">` **без `href` і без `tabindex`**. Такий елемент не потрапляє в послідовність Tab, тому користувач клавіатури не може відкрити кошик і, відповідно, не може завершити покупку. axe цього не виявляє, бо роль і доступне ім'я задані коректно.
- **Критерій WCAG:** 2.1.1 Keyboard (A)
- **Кого зачіпає:** користувачів лише клавіатури, скрінрідерів (у режимі фокуса), голосового керування.
- **Кроки відтворення:**
  1. Увійти як `standard_user`.
  2. Додати товар у кошик.
  3. Натискати Tab/Shift+Tab по всій сторінці.
- **Очікувано:** фокус потрапляє на іконку кошика, Enter відкриває `/cart.html`.
- **Фактично:** після кнопки «Open Menu» фокус переходить одразу на селектор сортування; кошик пропускається. Єдиний обхідний шлях — ввести URL вручну.
- **Рекомендація:** використати справжнє посилання `<a href="/cart.html">` (без `role="button"`, бо це навігація) або `<button>` з обробником.
- **Severity:** Critical
- **Джерело:** клавіатура (`inventory.keyboard.spec.ts`, `checkout.keyboard.spec.ts`)

## A11Y-003

**Після закриття меню фокус не повертається на кнопку «Open Menu»**

- **Сторінка/стан:** будь-яка авторизована сторінка, бургер-меню
- **Опис:** після закриття меню клавішею Escape або кнопкою «Close Menu» фокус переходить на `<body>`. Наступний Tab починає обхід з початку документа. Поведінка до того ж нестабільна: у WebKit фокус на ~0.3 s потрапляє на кнопку, а потім все одно падає на `<body>`. У Firefox під навантаженням фокус іноді не переходить у відкрите меню.
- **Критерій WCAG:** 2.4.3 Focus Order (A)
- **Кого зачіпає:** користувачів клавіатури та скрінрідерів: втрачається контекст, скрінрідер нічого не оголошує.
- **Кроки відтворення:**
  1. Tab до «Open Menu».
  2. Enter (меню відкривається, фокус на «All Items»).
  3. Escape.
- **Очікувано:** фокус на кнопці «Open Menu».
- **Фактично:** `document.activeElement === document.body`.
- **Рекомендація:** зберігати посилання на тригер і викликати `trigger.focus()` після закриття (після завершення анімації).
- **Severity:** Medium
- **Джерело:** клавіатура (`menu.keyboard.spec.ts`)

## A11Y-004

**Клавіша Space не активує кнопку меню і пункти меню з `role="button"`**

- **Сторінка/стан:** бургер-меню
- **Опис:**
  1. Space на нативній `<button id="react-burger-menu-btn">` не відкриває меню (Enter відкриває). Так у всіх трьох рушіях.
  2. Пункти меню «All Items», «Logout», «Reset App State», «Dynamic Catalog» — це `<a href="#" role="button">`. Роль `button` обіцяє активацію клавішею Space, але посилання реагує лише на Enter, а Space прокручує сторінку.
- **Критерій WCAG:** 2.1.1 Keyboard (A); 4.1.2 Name, Role, Value (A) — заявлена роль не відповідає поведінці.
- **Кого зачіпає:** користувачів клавіатури та скрінрідерів, які звикли активувати кнопки клавішею Space.
- **Кроки відтворення:** Tab до «Open Menu» → Space; або відкрити меню → фокус на «Reset App State» → Space.
- **Очікувано:** меню відкривається; дія пункту виконується.
- **Фактично:** нічого не відбувається / сторінка прокручується (`scrollY` 0 → 390).
- **Рекомендація:** не перехоплювати Space на кнопці меню; для пунктів-дій використати `<button>` або додати обробник `keydown` для Space з `preventDefault()`.
- **Severity:** Medium (є обхідний шлях через Enter)
- **Джерело:** клавіатура (`menu.keyboard.spec.ts`)

## A11Y-005

**Кнопка меню не повідомляє стан розгорнутості**

- **Сторінка/стан:** шапка, кнопка «Open Menu»
- **Опис:** `<button id="react-burger-menu-btn">Open Menu</button>` не має `aria-expanded` і `aria-controls`. Скрінрідер не оголошує, відкрите меню чи закрите.
- **Критерій WCAG:** 4.1.2 Name, Role, Value (A)
- **Кого зачіпає:** користувачів скрінрідерів.
- **Кроки відтворення:** перевірити атрибути кнопки в DevTools до й після відкриття меню.
- **Очікувано:** `aria-expanded="false"` → `"true"`, `aria-controls` вказує на панель меню.
- **Фактично:** атрибутів немає.
- **Рекомендація:** додати `aria-expanded` і `aria-controls`, синхронізовані зі станом меню.
- **Severity:** Medium
- **Джерело:** ручна перевірка, автотест `menu › button exposes its expanded state`

## A11Y-006

**Фокус губиться після зміни стану товару в кошику та після сортування**

- **Сторінка/стан:** inventory
- **Опис:**
  1. Після Enter на «Add to cart» кнопка замінюється новим елементом «Remove», і фокус переходить на `<body>`. Те саме відбувається у зворотному напрямку.
  2. Після зміни сортування з клавіатури (ArrowDown на `<select>`) список перерендерюється, і `<select>` втрачає фокус. Наступна стрілка вже нічого не змінює.

  Браузери частково пом'якшують проблему (наступний Tab продовжує обхід «з місця»), але скрінрідер не оголошує новий стан кнопки, а користувач втрачає орієнтацію.
- **Критерій WCAG:** 2.4.3 Focus Order (A)
- **Кого зачіпає:** користувачів скрінрідерів і клавіатури.
- **Кроки відтворення:** Tab до «Add to cart» → Enter → перевірити `document.activeElement`.
- **Очікувано:** фокус лишається на кнопці (тепер «Remove»); `<select>` зберігає фокус.
- **Фактично:** `document.activeElement === document.body`.
- **Рекомендація:** змінювати текст і стан тієї самої кнопки замість заміни елемента (або повертати фокус програмно); не перемонтовувати `<select>` під час сортування.
- **Severity:** Medium
- **Джерело:** клавіатура (`inventory.keyboard.spec.ts`)

## A11Y-007

**Enter у полі форми checkout скасовує оформлення замовлення**

- **Сторінка/стан:** checkout-step-one (Your Information)
- **Опис:** у формі першою йде `<button id="cancel">` без атрибута `type`, тобто за замовчуванням `type="submit"`, а вже за нею — `<input type="submit" value="Continue">`. Неявне надсилання форми (Enter у текстовому полі) активує **першу** submit-кнопку, тобто «Cancel». Користувач повертається в кошик, а введені дані зникають.
- **Критерій WCAG:** прямого порушення окремого критерію немає; проблема суперечить принципу 3.2 Predictable та очікуваній клавіатурній конвенції (2.1.1 Keyboard). Для користувача клавіатури це серйозний функціональний дефект.
- **Кого зачіпає:** усіх користувачів клавіатури (включно з тими, хто просто натискає Enter після введення індексу).
- **Кроки відтворення:**
  1. Додати товар → Cart → Checkout.
  2. Заповнити First Name, Last Name, Zip.
  3. Натиснути Enter у полі Zip.
- **Очікувано:** перехід на checkout-step-two (як після «Continue»).
- **Фактично:** перехід на `/cart.html`, дані форми втрачено.
- **Рекомендація:** `<button type="button" id="cancel">`.
- **Severity:** High
- **Джерело:** клавіатура (`checkout.keyboard.spec.ts`)

## A11Y-008

**Однаковий заголовок сторінки на всіх екранах**

- **Сторінка/стан:** усі сторінки
- **Опис:** `<title>` на кожній сторінці — «Swag Labs». Заголовок не описує тему чи призначення сторінки (Products, Your Cart, Checkout: Your Information, …), і в SPA він не оновлюється під час навігації.
- **Критерій WCAG:** 2.4.2 Page Titled (A)
- **Кого зачіпає:** користувачів скрінрідерів (заголовок оголошується першим), користувачів з кількома вкладками, людей з когнітивними порушеннями.
- **Кроки відтворення:** пройти login → inventory → cart → checkout і порівняти `document.title`.
- **Очікувано:** наприклад, «Products | Swag Labs», «Your Cart | Swag Labs».
- **Фактично:** завжди «Swag Labs».
- **Рекомендація:** оновлювати `document.title` при кожній зміні маршруту.
- **Severity:** Medium
- **Джерело:** ручна перевірка

## A11Y-009

**Поля форм не мають видимих підписів — лише placeholder**

- **Сторінка/стан:** login (Username, Password), checkout-step-one (First Name, Last Name, Zip/Postal Code)
- **Опис:** доступне ім'я задане через `aria-label`, тому axe не фіксує порушення. Але видимого `<label>` немає: підказкою слугує лише placeholder, який зникає після початку введення. Через це під час перевірки чи виправлення даних не видно, яке поле яке.
- **Критерій WCAG:** 3.3.2 Labels or Instructions (A)
- **Кого зачіпає:** людей з когнітивними порушеннями та порушеннями пам'яті, користувачів екранної лупи; також користувачів голосового керування, якщо видимий текст не збігається з доступним ім'ям.
- **Кроки відтворення:** почати вводити текст у поле — підказка зникає.
- **Очікувано:** постійно видимий `<label for="…">`.
- **Фактично:** лише `placeholder` + `aria-label`.
- **Рекомендація:** додати видимі `<label>` (можливий варіант — «floating label», що лишається видимим після введення).
- **Severity:** Medium
- **Джерело:** ручна перевірка

## A11Y-010

**Помилки валідації не пов'язані з полями програмно**

- **Сторінка/стан:** login:error, checkout-step-one:validation-errors
- **Опис:** текст помилки виводиться в `<h3 role="alert">` і оголошується скрінрідером, тобто вимогу 3.3.1 формально виконано. Проте поля з помилкою не мають `aria-invalid="true"` і `aria-describedby`, а червоні іконки біля полів (`svg role="img"`) не мають доступного імені. Повернувшись до поля, користувач скрінрідера не дізнається, що воно некоректне. Крім того, `role="alert"` на `h3` — недопустима для заголовка роль (axe best-practice `aria-allowed-role`).
- **Критерій WCAG:** 3.3.1 Error Identification (A) — рекомендація щодо покращення; 1.3.1 Info and Relationships (A)
- **Кого зачіпає:** користувачів скрінрідерів.
- **Кроки відтворення:** на checkout-step-one натиснути Continue з порожньою формою й перевірити атрибути полів.
- **Очікувано:** `aria-invalid="true"` + `aria-describedby="<id помилки>"` на відповідному полі.
- **Фактично:** атрибутів немає.
- **Рекомендація:** зв'язати повідомлення з полем; для контейнера помилки використати `<div role="alert">` замість `<h3>`.
- **Severity:** Low
- **Джерело:** ручна перевірка, axe best-practice

## A11Y-011

**На сторінках немає `h1` і логічної структури заголовків**

- **Сторінка/стан:** усі сторінки (на checkout-complete є лише `h2`)
- **Опис:** назви сторінок («Products», «Your Cart», «Checkout: Overview») реалізовано як `<span class="title">`. Логотип «Swag Labs» — `div`. Користувачі скрінрідерів не можуть швидко перейти до основного контенту через навігацію заголовками.
- **Критерій WCAG:** 1.3.1 Info and Relationships (A); axe best-practice `page-has-heading-one`
- **Кого зачіпає:** користувачів скрінрідерів.
- **Кроки відтворення:** переглянути список заголовків (NVDA: Insert+F7; DevTools → Accessibility tree).
- **Очікувано:** `h1` з назвою сторінки.
- **Фактично:** заголовків немає.
- **Рекомендація:** `<h1 class="title">Products</h1>` тощо.
- **Severity:** Low
- **Джерело:** axe (теги best-practice, поза скоупом CI-сканування) + ручна перевірка

## Ручні перевірки без дефектів

| Перевірка | Результат |
|---|---|
| axe `incomplete`: `color-contrast` для `.active_option`, `select`, описів товарів (axe не зміг визначити фон через псевдоелемент) | Перевірено вручну: текст `#132322` на `#FFFFFF` ≈ **15:1**, проходить 1.4.3 Contrast (Minimum) |
| Keyboard trap у меню (2.1.2 No Keyboard Trap) | Немає: фокус виходить з меню в обидва боки (Tab / Shift+Tab) |
| Порядок Tab на login та в картці товару | Логічний: Username → Password → Login; зображення → назва → кнопка |
| Закрите меню не потрапляє в Tab-послідовність | Так: пункти мають `tabindex="-1"` і `aria-hidden="true"` |

## Примітка щодо WebKit

WebKit (як і Safari з вимкненим налаштуванням «Press Tab to highlight each item») **не включає посилання** в послідовність Tab. Це поведінка рушія, а не дефект сайту, тому тести, яким потрібен Tab по посиланнях, у WebKit пропускаються з поясненням.

## Обмеження автоматизації

За оцінками Deque, axe-core автоматично виявляє приблизно 30–57 % проблем WCAG (залежно від методики підрахунку). Цей проєкт це добре ілюструє: **0 порушень від axe проти 11 проблем**, знайдених клавіатурними тестами та вручну.

| Що перевіряє автоматизація | Чого вона не бачить (або бачить частково) |
|---|---|
| Наявність доступного імені, ролі, `alt`, `lang`, коректність ARIA-атрибутів | Чи **логічні** назви й порядок: `aria-label` є, але видимого підпису немає (A11Y-009) |
| Контраст тексту, якщо фон можна обчислити | Контраст поверх зображень, градієнтів і псевдоелементів (axe повертає `incomplete`) |
| Статичну розмітку в момент сканування | Поведінку: куди переходить фокус, чи працює Space, чи повертається фокус (A11Y-003, -004, -006) |
| Що елемент має роль `button` | Що він **фокусується** і **активується** з клавіатури (A11Y-002) |
| — | Видимість індикатора фокуса (A11Y-001): перевіряється окремим тестом через computed style |
| — | Наслідки дій: Enter у формі запускає «Cancel» (A11Y-007) |
| — | Якість оголошень скрінрідера, зрозумілість текстів, когнітивне навантаження |

**Що зроблено поверх axe:**
- клавіатурні тести у трьох рушіях (Tab-порядок, Enter/Space/Escape, повернення фокуса, keyboard trap, видимість фокуса);
- ручна перевірка CSS (`:focus { outline: none }`), атрибутів ARIA, заголовків сторінок і структури заголовків;
- ручна перевірка контрасту для результатів axe `incomplete`.

**Що не автоматизовано:** перевірка скрінрідером (див. нижче), масштабування до 200 %/400 % і reflow (1.4.4, 1.4.10), керування голосом, когнітивна доступність текстів.

## Перевірка скрінрідером

_Розділ заповнює QA вручну (NVDA + Firefox/Chrome на Windows, VoiceOver + Safari на macOS)._

Рекомендований чек-лист:
- [ ] Логін: оголошення полів і помилки «Epic sadface…» (`role="alert"`)
- [ ] Inventory: назва сторінки та заголовки (A11Y-008, A11Y-011), оголошення «Add to cart» → «Remove» (A11Y-006)
- [ ] Меню: оголошення стану expanded/collapsed (A11Y-005), повернення фокуса (A11Y-003)
- [ ] Кошик: чи доступне посилання в режимі перегляду (virtual cursor) — A11Y-002
- [ ] Checkout: зв'язок помилок із полями (A11Y-010), підсумок замовлення на step two
